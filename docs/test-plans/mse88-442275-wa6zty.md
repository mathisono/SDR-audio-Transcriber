# MSE-88 field test: 442.275 MHz speech and CW identification

Status: **planned; capture has not been started by adding this document**.
Created: 2026-09-24. Owner/operator: Mathison Ott.

This is the first received-RF campaign under [DEVELOPMENT_PLAN.md](../../DEVELOPMENT_PLAN.md),
using the [recording corpus tools](../recording-corpus.md). The operator has specified
442.275 MHz and identified the target as the WA6ZTY repeater, which sends CW IDs.
These are target/expectation fields, not evidence that any particular clip contains
that ID or that reception has been verified on the new SDR.

The intended host is MSE-88 with a **new SDR**. Its model, serial, driver, actual gain,
frequency correction, antenna and current availability remain to be discovered on
that host. Do not assume that the new radio is RTL-SDR compatible.

This document was prepared against corpus branch commit
`654f1fa575bff2160b64a8d0ba8a543d406b3038`. The speech-first and corpus prerequisites
are PR #1 and PR #2. Check their live state before testing; the old `main` alone does
not contain those fixes. Use an isolated worktree and private test directories.
Adding this plan does not merge a PR, install software or change production.

## 1. Objective and fixed scope

Prove that this receiver can preserve intelligible RF audio and produce independently
measured speech and CW results. Keep speech the primary deliverable. Capture failure,
speech failure and CW failure are three separate outcomes.

| Item | Campaign setting |
| --- | --- |
| Host | MSE-88, verified on the actual machine |
| Receive frequency | **442,275,000 Hz** |
| Initial mode | Analog narrowband FM; confirm received audio during preflight |
| Coverage | One fixed receive channel, not a scan of the whole 70 cm band |
| Expected station ID | WA6ZTY, for comparison only after reference review |
| Transmit behavior | None: receive-only; no PTT, repeater activation or test transmissions |
| Initial archive | Continuous mono signed 16-bit PCM WAV, proposed 24,000 samples/second |
| File rotation | 60-second files with consecutive order recorded; preserve the short final file |
| Gating | None during the baseline: no audio squelch, speech VAD or receive-tone gate before archival |
| Speech baseline | Existing faster-whisper `small.en`, English, CPU INT8, beam size 5, VAD in the speech branch only |
| Cleanup and automatic labels | Off |
| CW | Internal DSP plus a separately configured real external decoder, when available |
| Retention | Keep original audio, references, hypotheses and metadata; no expiry or deletion |

The 24 kHz rate is a **proposed baseline**, not a measured capability of the new SDR.
The driver must produce actual PCM at the declared rate. The RF/channel filter,
demodulation rate and PCM rate are distinct settings; log each separately. Do not
silently narrow the IF until the signal's deviation/occupied bandwidth and recovered
audio have been checked. Record any different supported rate explicitly and start
a new session when changing settings.

The first archive is demodulated RF audio. It does not by itself satisfy the later
repeatable I/Q-to-audio/baseband gate. See section 8 for that separate step.

## 2. New-radio preflight: mandatory before opening the receiver

1. Verify hostname, checkout/commit, Python environment, driver version, CPU resources,
   available storage and time synchronization. Locate the actual checkout rather
   than assuming a username or path. Preserve unrelated working changes.
2. Inventory SDRs without taking an active device from another process. Record model,
   unique serial/selector, USB path and antenna arrangement. Inspect existing SDR
   processes/services. Do not default to device index 0, retune another service or
   stop an unrelated receiver. If ownership or device identity is ambiguous, stop
   and ask which device is the new one.
3. Determine the correct driver. If RTL-SDR compatible, confirm the installed
   `rtl_fm` options and supported tuner gains. Otherwise use a verified driver and
   equivalent single-channel demodulation path; do not launch rtl_fm blindly.
4. Use a new, device-specific capture profile. **Do not reuse the old radio's PPM,
   gain or RMS threshold.** Zero PPM may be an explicitly uncalibrated starting
   point for an exploratory session, never a claimed calibration. Check drift
   after warm-up; measure alignment using appropriate reference evidence. The
   received CW audio pitch alone does not establish the SDR's RF frequency error.
   Repeater alignment is not automatically a calibrated absolute frequency reference.
5. On the unused, identified device, tune receive-only to 442.275 MHz. Check for
   readable audio, correct playback speed, clipping, overload and adjacent-channel
   interference. Choose and record gain; do not maximize it blindly. Confirm the
   actual PCM rate, channels and sample width, not only command-line arguments.
6. Save a private manifest with real hardware settings, software/model versions,
   selected device, UTC start, session ID, calibration status, filter/de-emphasis
   settings and exact commands. Unknown values stay null/unknown. Keep the expected
   repeater callsign out of decoder prompts and station-label state.

**Launcher limitation at the reviewed commit:** `start_rtl_fm_receiver.sh` reads
remembered shared PPM and does not expose `-d`/a device selector. It is not sufficient
for safely selecting this new radio. Use an explicitly selected device in a
supervised pipeline, or add/test an explicit selector and isolated config support
before using that launcher. Do not overwrite the shared receiver config.

Preflight passes when there is an identified, available device and a verified
single-channel PCM stream with an explicit storage/shutdown plan. If the channel
is quiet, report that signal/audio identity is not yet confirmed; do not manufacture
an ID or claim a failed repeater just because no traffic was heard.

## 3. Acquisition sequence

### A. Short checkout, then a bounded two-hour shakedown

Start with 10 minutes of continuous audio to verify files, timing, rate and storage.
Continue to a maximum two-hour shakedown only when the recording path is healthy.
This is an operational limit, not an expectation that an ID must occur in that time.
Inspect early and late files and listen across at least one file boundary.

Archive all input before any speech/CW detector. This makes silence/noise and missed
activity observable. `clip_writer.py --threshold 0` keeps this baseline continuous;
`--min-sec 0` preserves a short final segment. At this setting hang and pre-roll do
not act as transmission gates. Disable receive-tone filtering: even a correct
access-tone listing would not prove that every ID carries that tone on output.

**Boundary accounting:** 60-second chunks are files, not independent transmissions.
An ID or word can cross a file boundary. Save sequence and cumulative sample ranges
in a session index, keep both chunks, and create documented joined/overlapping
replay inputs when needed. Keep derived variants in the same dataset split as the
parents. Do not count one ID in two neighboring chunks as two independent successes.
The existing corpus does not automatically create these joins or detect shared
I/Q/audio parents; those relationships must be recorded in the campaign manifest.

### B. Bounded 24-hour baseline, only after shakedown passes

Start a **new session**, lock the acquisition settings and record for at most
24 hours. Stop earlier on storage, device, data-flow or integrity faults. Do not
silently extend into indefinite monitoring if traffic is sparse. Report which
sample targets were not met, then decide whether another bounded session is needed.
Do not auto-delete earlier data to make room.

At 24 kHz x 1 channel x 2 bytes/sample, continuous audio is 48,000 bytes/second:

- Two hours: 345.6 MB for one PCM archive; about 691.2 MB with the corpus copy.
- Twenty-four hours: 4.1472 GB for one PCM archive; about 8.2944 GB with the corpus copy.

These are decimal payload calculations, before WAV headers, logs, SQLite, derived
clips, model weights and other recordings. Raw I/Q has a separate, larger budget.

Proposed guards: a **12 GiB total campaign allocation** and an **8 GiB free-space
reserve** on each filesystem used. Before launch, verify sufficient remaining room
for the planned acquisition plus the reserve. Stop acquisition and collection before
either limit is crossed; account for archive and corpus copies, partial files and
logs together. Existing data elsewhere must not be deleted. Make changes to these
limits explicit in the private manifest.

Check every minute for device/process exit, no new PCM, stale file publication,
free space and campaign size. If decoding runs concurrently, also check its backlog,
CPU/memory and capture errors. Give acquisition priority; pausing inference is
preferable to losing RF. A lack of speech is not a missing-PCM fault.

A session supervisor must own only the processes it launched. On normal stop or a
guard event, stop the SDR producer first, allow the writer to drain EOF and finalize,
then stop collection after the last finalized files are imported. Use bounded waits
and report forced termination/partial files. Do not use broad `pkill` commands.
No such supervisor is deployed by this document: OpenClaw/the local operator must
establish and verify this bounded execution before unattended recording.

### C. Independent holdout session

Use a later, separate acquisition session for `--split test`. Keep exploration and
parameter tuning in validation sessions. A different time interval on this same
repeater is still a **single-site** evaluation, not proof of general performance.
Do not randomly split adjacent chunks of one transmission between validation/test.
When comparing acquisition changes, use controlled I/Q replay or clearly report
that different live traffic is an unpaired comparison.

## 4. Pilot sample and review targets

These are collection goals, not promised traffic or a statistically validated
retention threshold. Keep every recording; do not collect only detector-positive
clips or discard failed decodes.

| Reviewed category | Initial goal | What it tests |
| --- | --- | --- |
| Intelligible speech | 50 independent transmissions | Word errors, numbers/callsigns, clipped beginnings/endings |
| CW identification | 20 separate received ID events | Exact ID recovery, character errors, missing/extra callsigns |
| Mixed speech and CW | 10 events if naturally present | Independent decoding when ID overlaps or follows voice |
| Noise/silence/tone controls | 50 reviewed windows | False speech, false CW IDs and confusion with steady/courtesy tones |
| Speech with no CW | Include at least 20 speech examples above | CW false-ID rate on genuine voice traffic |

Spread review across early/late capture and clear/difficult conditions. Add a
preselected uniform/random sample from the full timeline as an audit against
selection bias. Mark weak received RF separately from distorted/weak user audio
being retransmitted by a strong repeater. Annotate what can actually be heard.

Reviewers should listen before seeing decoder text where practical. Use actual
reference text; `WA6ZTY` is not an instruction to fill in an unintelligible ID.
Empty string means confidently absent; null means unreviewed/unintelligible for
that target. Preserve and report the latter rather than treating it as a negative
control. Record speech/CW overlap, file boundaries, clipping and reviewer ambiguity
in private review notes. Do not use an LLM's cleaned text as ground truth.

**Blind decoder rule:** no callsign hints/whitelists in Whisper prompts, CW candidate
ranking, filenames or automatic labels. The operator-supplied callsign can appear
in this plan and in a separately reviewed reference. A different decoded callsign
is a disagreement to investigate, not an output to autocorrect. Speech from an
operator through the repeater must not rename the repeater.

Repeated recognition of one station's fixed ID is useful but narrow evidence.
Keep existing alternate-callsign synthetic fixtures and speech/noise controls;
add independently reviewed other stations before generalizing CW identification.

## 5. Execution sketch for the local operator/OpenClaw

This is a component wiring example, **not an unattended service**. Run it only
under the ownership, duration, storage and shutdown supervision above. It applies
only after RTL-SDR compatibility is confirmed. For other hardware, use its verified
single-channel capture path and the same WAV/manifest contract.

Use an isolated checkout containing the prerequisite code and set these variables
from preflight. Missing values intentionally stop the example; do not paste guessed
serials, gains or calibration values. `PPM=0` is permissible only when explicitly
recorded as an uncalibrated exploratory start. `SESSION_ROOT` must be a new, private
session directory; `PY` is an absolute path to the selected Python executable.

```bash
# Required preflight values: RTL_DEVICE, GAIN_DB, PPM, PY, SESSION_ROOT.
: "${RTL_DEVICE:?Select the confirmed new device, not implicit index zero}"
: "${GAIN_DB:?Choose and record a supported gain}"
: "${PPM:?Set device-specific correction and record its calibration status}"
: "${PY:?Absolute path to the selected Python executable}"
: "${SESSION_ROOT:?Absolute path to a new private session directory}"
umask 077
mkdir -p "$SESSION_ROOT/archive" "$SESSION_ROOT/tmp" "$SESSION_ROOT/logs"
printf '*\n' > "$SESSION_ROOT/.gitignore"
set -o pipefail

# The supervisor must record process identities and bound runtime/storage.
# No -l squelch, CTCSS receive gating, automatic station hints or shared config.
rtl_fm -d "$RTL_DEVICE" -M fm -f 442.275M \
  -s 24000 -r 24000 -g "$GAIN_DB" -p "$PPM" - \
  2>"$SESSION_ROOT/logs/receiver.log" | \
  "$PY" scripts/clip_writer.py \
    --source MSE-88 --receiver rx-new-sdr \
    --frequency-hz 442275000 --mode nfm --sample-rate 24000 \
    --threshold 0 --pre-roll-ms 0 --hang-ms 2000 \
    --min-sec 0 --max-sec 60 \
    --queue "$SESSION_ROOT/archive" --tmp "$SESSION_ROOT/tmp" \
    >"$SESSION_ROOT/logs/writer.log" 2>&1
```

Keep this archive independent of ASR success. **Do not point the live speech worker
at `archive`**; it would move files the collector is watching. First collect from
this finalized archive, then evaluate immutable corpus copies. The worktree's
existing `runtime/queue`, `processing`, `done` and services are not part of this test.
If adding live transcription later, create separate jobs from immutable archived
files; never race two consumers for the original file.

After creating a real `settings.json` object and a unique session ID, the collector
can run alongside capture under the same duration/disk supervisor:

```bash
# CORPUS_ROOT is private and outside every HTTP server's document root.
: "${CORPUS_ROOT:?Private corpus directory}"
: "${SESSION_ID:?Unique session identifier}"
"$PY" scripts/recording_corpus.py --root "$CORPUS_ROOT" \
  collect "$SESSION_ROOT/archive" --session "$SESSION_ID" \
  --split validation --origin rf --settings "$SESSION_ROOT/settings.json" \
  --watch
```

Use `--split test` for the later holdout session. Session settings and splits are
immutable in this tool; do not recycle a session ID after changing them. Keep all
observations of exact duplicates and all joined/cropped parent variants in one
split. After source/writer shutdown, stop watch mode and run one final one-shot
collection after files have settled.

Add independently checked references using the runbook, then run:

```bash
"$PY" scripts/recording_corpus.py --root "$CORPUS_ROOT" \
  run --engine speech --split validation --origin rf \
  --model small.en --device cpu --compute-type int8 --timeout 180

"$PY" scripts/recording_corpus.py --root "$CORPUS_ROOT" \
  run --engine cw --split validation --origin rf --timeout 60
```

The evaluator runs the entire selected split, not just reviewed positives. It
cold-loads the speech model for each clip; budget runtime accordingly and prefer
an offline run during the initial campaign. A cold-process benchmark must not be
reported as warm streaming throughput. `--engine external-cw` requires an actually
installed/verified command. A shim with no backend is blocked, not a second success.

## 6. Measurements, checkpoints and progression

Checkpoints: preflight, first finalized file, 10 minutes, two-hour close, 24-hour
close if approved by the shakedown, then human-reference/decoder comparison. These
are local execution checkpoints, not ChatGPT reminders or promises of background
monitoring. Record actual timestamps and pending work.

Report:

- Receive/capture: device and settings, scheduled versus recorded duration, frame
  counts, file boundary continuity, gaps/overruns, invalid/partial files, waveform
  clipping, disk use and stop reason. ClipWriter timestamps are approximate wall
  time; derive relative timing from frame counts. Precise I/Q-clock timing remains
  a separate future gate.
- Speech: raw transcript, WER on reviewed intelligible speech, required-token errors,
  false text on negatives, unreviewed count and ASR failures. Score original output,
  not cleanup. Keep unintelligible cases with explicit coverage limits.
- CW: per-engine text, character errors, exact observed-ID matches, missed IDs,
  false/extra callsigns and disagreements. Count independent ID events, not files
  or repeated decoding of the same audio. Do not treat internal scores as calibrated
  probabilities.
- Runtime: model-load and inference time separately, processed/audio seconds,
  queue backlog and resource use on MSE-88. Keep capture healthy before increasing
  parallel decoder work.

Proposed **pilot** progression gates, to be locked before scoring the held-out set:
no silent loss/corruption of finalized audio; every optional decoder failure retains
the evidence; pooled WER <= 20% on the reviewed intelligible-speech subset; at least
19 of 20 independent intelligible CW IDs recovered exactly; zero false repeater
bookmarks (automatic promotion is disabled). Report false decoder callsign/text
counts even when nothing is promoted. These small counts do not establish a low
population false-positive rate or authorize deletion. Missing sample targets mean
insufficient data, not a pass or a reason to lower the goal after seeing outputs.

First prioritize acquisition, missing beginnings/endings and false text. Change
one factor per validation experiment, use paired audio for decoder comparisons,
and rerun the unchanged holdout only for the predeclared acceptance evaluation.
Do not tune repeatedly against the holdout.

## 7. Storage, privacy and retention

All received audio/transcripts/settings remain private on the authorized host.
No public HTTP service or public GitHub recordings. Commit only code, this plan and
non-sensitive aggregate results explicitly suitable for publication. Keep source
and copy paths out of public logs where they expose private host details.

No expiry, audio deletion, metadata deletion or confidence-based cleanup in this
campaign. The corpus `retention-plan` remains audit-only. Storage exhaustion stops
capture; it does not erase training/test evidence. Back up audio and use a consistent
SQLite backup, including the WAL considerations in the corpus runbook.

## 8. Follow-on I/Q and waterfall work

Once this fixed-channel campaign is dependable, preserve a short, bounded I/Q
recording with accurate datatype/rate/tuning/time metadata and replay the single
FM chain. With one SDR there must be one hardware owner: do not run independent
rtl_fm and rtl_sdr captures against the same device simultaneously. Use a supported
shared-I/Q source or a deliberate, separately logged capture session.

Compare alternate demodulation/filter settings on identical I/Q, align sample
ranges and filter delays, then integrate receive-time transcript events into the
selected web waterfall. Multi-channel discovery and automatic CW bookmarks remain
later milestones. This one-repeater audio campaign is not evidence those features
are already implemented.
